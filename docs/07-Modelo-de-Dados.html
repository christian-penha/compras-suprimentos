Modelo de Dados Definitivo — Compras e Suprimentos

Grupo Perfil de Educação · v1.0 · 30/09/2026

Este documento consolida todas as decisões tomadas entre 09 e 30/09/2026 num modelo de dados pronto para virar código Django. Os models abaixo são esqueletos deliberados — campos, chaves, unique_together, e principalmente comentários explicando o motivo de cada decisão não óbvia. Não é código para copiar e rodar sem revisão; é a estrutura que evita o retrabalho que discutimos.

Convenção: todo model de negócio herda de TenantModel (abaixo) e AuditModel implicitamente, salvo indicação contrária.

0. Decisão de arquitetura que fica registrada aqui, por ainda não ter sido fechada com você

Estratégia de multi-tenancy: linha a linha (row-level), não schema-per-tenant.

Schema-per-tenant (django-tenants) dá isolamento estrutural mais forte — um bug de query não vaza dado entre tenants, porque o banco nem enxerga o schema do outro. É o que eu recomendaria para um SaaS já em operação com múltiplos clientes.

Mas você está sozinho, com um tenant real (o Grupo Perfil) por um bom tempo, e schema-per-tenant adiciona complexidade operacional real: migração por schema, criação de schema por tenant, conexão de banco mais delicada. Para um desenvolvedor só, isso é custo hoje por um benefício que só aparece quando houver o segundo cliente.

Adoto row-level: todo model relevante tem tenant = ForeignKey(Tenant), um manager padrão que filtra automaticamente pelo tenant corrente (via contextvars, setado no middleware a partir do usuário autenticado), e a regra não-negociável de que nenhuma view usa o manager objects bruto de um model tenant-aware sem passar pelo escopo. Eu formalizo isso com um teste automatizado que varre todas as views e falha se encontrar uma consulta não escopada — trago isso no prompt inicial.

Se e quando houver um segundo cliente de verdade, a migração para schema-per-tenant é um projeto isolado, não uma reescrita do domínio — os models não mudam, muda a camada de roteamento de conexão.

class Tenant(models.Model):
    """O grupo econômico. Uma linha só hoje (Grupo Perfil), preparado para mais."""
    nome = models.CharField(max_length=200)
    slug = models.SlugField(unique=True)
    ativo = models.BooleanField(default=True)
    criado_em = models.DateTimeField(auto_now_add=True)


class TenantModel(models.Model):
    """Mixin abstrato: todo model de negócio herda daqui."""
    tenant = models.ForeignKey(Tenant, on_delete=models.PROTECT)
    objects = TenantAwareManager()   # filtra automaticamente pelo tenant corrente
    all_objects = models.Manager()   # escape hatch explícito, uso só em management commands/admin

    class Meta:
        abstract = True


class Empresa(TenantModel):
    """
    Pessoa jurídica (CNPJ). Quem compra: fornecedor, OC e nota fiscal
    referenciam Empresa, nunca Filial diretamente.

    Hoje: 4 filiais numa Empresa, 1 filial em Empresa separada.

        unique_together = [("tenant", "cnpj")]

# apps/estoque/models.py

class MovimentacaoEstoque(TenantModel):
    """
    FONTE DA VERDADE do estoque (decisão 09/09). NUNCA editar ou deletar —
    correção sempre por contra-movimento vinculado (`estorno_de`).

    tipo: ENTRADA_COMPRA, ENTRADA_SEM_CUSTO, SAIDA_CONSUMO, TRANSFERENCIA,
          DEVOLUCAO (existe no enum, SEM interface no MVP — decisão O11),
          AJUSTE_INVENTARIO, ESTORNO.

    origem: COMPRADO | SEM_CUSTO — dimensão que impede que material a R$0
    dilua o custo médio do material comprado (decisão 09/09). Preenchida em
    toda ENTRADA e herdada na SAIDA (o que sai carrega a origem de onde saiu).

    Valor unitário é CONGELADO aqui, nunca recalculado depois — é o que
    garante que um relatório histórico não mude sozinho (ver modelo contábil).
    """

O que fica de fora do MVP, deliberadamente

Listado aqui para não ser reintroduzido por acidente durante o desenvolvimento:

  • Devolução de sobras (model/enum existe, sem interface)
  • Compra direta (model existe, avaliação/tela só na fase 4)
  • Regra de aprovação por % de centro de custo excedido (model existe, ativo=False)
  • Serviços terceirizados
  • Integração automática com o Prodados (só o campo codigo_prodados nos cadastros)
  • Conciliação contábil formal
  • Captura automática de NF-e via Sefaz (só upload manual de XML)
  • Controle orçamentário e controle patrimonial
  • Termo de responsabilidade digital para kits de professores
  • Schema-per-tenant (linha a linha por ora — ver seção 0)
